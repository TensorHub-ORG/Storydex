## 1. 结论

下一步不应直接按静态代码推断继续扩大改动，而应先使用现有 OpenCode Provider 配置，对 Storydex 正常 HTTP/SSE Agent 主链路进行隔离的真实运行，取得当前版本的完整事件、耗时、回合、工具、Token、重试和停止原因证据，再决定优化重点。

已有 P0/P1 工作已经解决了会话恢复、有界读取、全文检索、暖态重复扫描、结构化压缩检查点和基础 Token 观测等问题。这些成果是后续治理的前提，但不代表慢响应专项已经完成。当前仍缺少足以说明真实 Provider 等待、持续生成、重复模型回合和上游重试成本的闭环证据，也未证明现有调度能及时阻止无进展扩张。

本阶段目标不是预先认定某个模块必须重构，而是让一次真实慢任务能够被可靠回答：时间耗在哪里、为什么产生这些模型回合、配置是否实际生效、重试是否合理、是否持续获得新进展，以及应该在哪个边界停止或恢复。

## 2. 已确认的现状

### 2.1 已基本完成的基础治理

- session 缺失、损坏和 workspace 不匹配不再静默恢复为空历史；首次绑定和持久化已有明确约束。
- `read_file` 已具备 revision、span、总量、截断状态和继续方式，长文本及 UTF-8 边界已有保护。
- FTS 已改为全文分块索引，错误与零命中可以区分；Wiki/FTS 暖态查询已迁移到已发布快照和后台增量刷新。
- 独立且未被主 Agent 消费的规划模型调用已经删除。
- Evidence Ledger v1、结构化 compaction checkpoint、Token shadow accounting 和基础生命周期 Trace 已落地。
- 已有隔离的真实主链路基线脚本和严格单工具夹具，可作为后续复测入口之一。

### 2.2 尚未闭环的问题

1. **输出预算的语义和实际请求可能不一致。** 当前代码中模型能力预算、主 Agent 每轮请求值和 Provider 协议默认值仍可能得到不同结果。现有证据不能证明用户配置或模型能力值最终按预期进入每一轮真实请求。

2. **Provider 原始网络阶段仍不可充分区分。** 生命周期 Trace 可以观察模型开始、输出事件、工具执行和重试，但部分首响应时间仍来自解码后事件或模型完成 fallback，不能可靠区分响应头等待、原始首字节等待和模型持续生成。

3. **多轮串行模型调用仍是主要风险。** 历史真实记录中，长任务的大部分时间消耗在多次串行模型回合和 Provider 等待，文件工具执行时间很低。当前尚未证明新版本在复杂任务中已经避免重复读取、重复规划或无新增证据的回合扩张。

4. **Agent 的止损边界仍偏粗。** 当前主要循环保护仍是较大的工具回合总上限。系统已有部分 Provider 超时、有限重试和重复工具统计，但阶段预算、整体时间边界、连续失败以及多轮无进展的停止行为尚未形成统一、可验收的闭环。

5. **现有检查点主要服务于上下文压缩。** 它可以保护权限、目标、计划和证据引用，但尚不能直接证明任意中断后都能从任务进度恢复，也不能证明恢复后不会重放已完成的写操作。

6. **reasoning 能力链路只完成了部分闭环。** 已有能力对象、请求计划、Provider wire 适配和前端选择约束，但未知模型或未声明模型仍可能无法应用用户选择。历史 Qwen 基线中请求 `low` 未实际发送，当前没有新的真实证据证明该现象已经消失。

7. **优化前后对比样本不足。** 现存报告主要是单文件、单工具短任务，且仍能观察到输出预算不一致和首字节 fallback。它们不能替代真实多工具长任务，也没有覆盖停止、恢复、权限拒绝和流中断等场景。

## 3. 本轮需要回答的核心问题

真实运行和后续优化应围绕以下问题收集证据，不先假设答案：

- 一次用户请求实际产生多少模型回合、工具调用和 Provider 尝试？每一轮为什么继续？
- 总耗时分别落在请求前准备、Provider 首响应、模型持续生成、工具执行、用户等待和重试恢复的哪一部分？
- 每轮逻辑输入、实际传输输入、缓存输入、输出和 reasoning Token 如何变化？是否随完整历史重复增长？
- 用户选择的 reasoning 档位和输出预算最终是否进入真实协议请求？未发送、降级或重试移除时，原因是否可观察？
- 重复工具调用发生时，文件 revision、证据覆盖或任务状态是否有变化？如果没有，为什么仍继续下一轮？
- Provider 重试发生在请求发送前、首字节前、已输出后还是流中断后？重试是否重复了已展示内容或已完成副作用？
- 任务停止时是否有明确原因，并保留了已经取得的结果和可恢复状态？
- 连续执行相同任务或后续回合时，bridge 初始化和完整上下文重传是否仍构成主要固定成本？

## 4. 推荐推进路线

### 阶段 A：建立当前版本真实基线

使用隔离 workspace 和 OpenCode Provider 配置副本，通过 Storydex 正常 API/SSE 路径运行，不直接绕过 Backend 调用 Rust Provider。至少保留一个严格只读短任务和一个能够稳定产生多个工具回合的代表性任务。

真实运行必须保留脱敏后的结构化报告，至少包括总耗时、每轮阶段时间、模型回合数、工具序列、Token、重试、配置诊断和最终停止状态。凭证、Authorization、完整提示词、reasoning 正文和敏感工具参数不得进入报告。

如果当前 Trace 无法回答第 3 节的问题，应先补足最小观测能力，再进行性能优化。不能使用推测值填充 Provider 原始时间，也不能把模型完成时间标记为网络首字节。

### 阶段 B：按实际占比确定优化重点

根据真实报告对问题归类：

- 若主要成本在 Provider 首响应或重试恢复，优先检查协议适配、请求参数、超时和重试行为。
- 若主要成本在长时间持续生成，优先检查输出预算、reasoning 配置、工具参数生成和停止条件。
- 若主要成本在多轮重复发送和重复决策，优先检查任务进展判定、证据复用、循环边界和上下文传输。
- 若主要成本在 bridge 初始化或上下文装配，先证明其占比和重复性，再评估运行时生命周期方向。
- 若工具本身成为瓶颈，再针对实际慢工具处理；不要沿用历史结论永久假设所有工具都快。

每次只处理报告中能够量化的主导问题。不同类别可以共享观测协议，但不应在一个改动中同时重写 Provider、Agent 循环、运行时生命周期和前端诊断。

### 阶段 C：补齐配置与调度闭环

在真实证据指向相应问题后，逐步确保以下结果成立：

- 模型能力、用户请求和 Provider 最终发送值之间有明确、可审计的关系。
- 各协议使用与其兼容的请求语义，降级、拒绝和重试不会静默改变用户选择。
- Agent 能基于阶段、时间、错误和任务进展及时停止无收益扩张，并返回明确原因。
- 中断和停止后的状态足以支持安全继续，已经完成的副作用不会被无条件重放。
- 前端能展示对用户有决策价值的运行状态和诊断，但不暴露敏感内容或把估算值伪装成 Provider 原始数据。

### 阶段 D：使用同一入口复测

所有优化必须使用与阶段 A 相同的 API 路径、workspace 结构、提示目标和验收条件复测。可以增加新场景，但不能更换原始夹具后声称性能改善。

至少比较：

- 总耗时及其阶段构成；
- 模型回合数和工具调用数；
- 首响应、首个可见输出和完整生成时间；
- 输入、输出、reasoning、缓存及实际传输指标；
- 重复工具调用和无进展回合；
- Provider 重试及其发生阶段；
- 最终停止原因、已有结果和恢复状态；
- reasoning 与输出预算的请求值、最终发送状态和降级原因。

性能波动应通过多次运行观察，不以一次更快作为完成依据。真实 Provider 的绝对耗时可以变化，重点是配置确实生效、无进展回合减少、错误归因可信，并且相同工作不会因循环或重试被无界放大。

## 5. 场景范围

第一批真实运行建议保持范围可控：

1. 严格只读单工具任务，用于验证基础生命周期、reasoning 和输出预算诊断。
2. 只读多工具任务，用于观察串行模型回合、重复读取和证据进展。
3. scoped 写入任务，用于观察计划、工具执行、检查点和副作用保护。
4. 可控失败场景，用于观察权限拒绝、Provider 重试、流中断或超时后的停止和恢复。
5. 同 session 后续回合，用于观察历史重传、证据复用和 bridge 固定成本。

不要求首轮同时跑完所有 Provider。先用当前实际可用的 OpenCode 配置获得可信主链路，再根据能力和协议差异增加 Qwen、DeepSeek 或其他模型对照。不同模型之间用于识别配置和协议差异，不用于简单宣称某个模型一定更快。

## 6. 完成标准

只有同时满足以下条件，才能认为本轮慢响应与调度治理完成：

1. 当前版本和优化后版本均有同口径、脱敏、可复现的真实主链路报告。
2. 报告可以区分请求准备、Provider 原始响应、持续生成、工具执行和重试恢复，而不是依赖不准确的 fallback 冒充原始指标。
3. 输出预算和 reasoning 的请求值、能力来源、最终发送值及降级原因可验证，Agent 预算与 wire 语义不存在无法解释的分歧。
4. 代表性多工具任务不会因重复规划、重复工具或无新增证据持续扩张；达到边界时返回明确停止原因。
5. Provider 重试有明确预算和阶段记录，部分输出或副作用不会在恢复时无条件重复。
6. 中断、停止和继续执行时，权限、目标、计划、证据和已完成动作保持一致。
7. 优化结果由聚焦回归、仓库标准门禁和真实主链路复测共同支持。
8. 若最终证据表明主要成本来自外部 Provider 本身，也必须能清楚证明 Storydex 没有额外放大回合、Token、重试或等待，而不是用“上游慢”结束分析。

## 8. 边界与禁止事项

- 不把历史短基线、静态代码推断或单次偶然加速当作当前真实结论。
- 不为得到更好数字而缩短任务目标、更换 fixture、减少必要验证或隐藏失败回合。
- 不通过单纯调大输出上限、工具回合数或超时来掩盖配置传递和无进展问题。
- 不用静默 fallback、吞错或无意义重试把 Provider/协议错误转换成成功。
- 不在缺少数据时提前实施长生命周期 worker、远端权威 session 或跨层大重构。
- 不记录凭证、完整提示词、reasoning 正文、敏感工具参数或用户作品正文；只保留完成诊断所需的脱敏统计和状态。
- 不修改真实用户项目；写入场景只能使用临时 workspace 和明确 scoped 权限。

## 9. 2026-08-13 阶段性真实执行结果

### 9.1 实际 OpenCode 配置与隔离边界

本轮实际读取当前机器的 OpenCode 配置，并选择 `ds/deepseek-v4-flash` 进行调用：

- Provider 适配器为 `@ai-sdk/openai-compatible`，通过基线脚本转换为临时 Storydex Provider 配置。
- 只复制被选中的 Provider 和模型，不保留其他 Provider，不写回用户 OpenCode 配置。
- 调用前后源配置 SHA-256 均为 `97A95683589D2949E3EEBFDA4A3D44624DDF29687ED80AB265340F903FECF370`。
- 结构化报告中不包含 API Key 字段、Authorization、完整提示词、reasoning 正文或模型响应正文。

输出预算与 reasoning 已形成真实 wire 闭环：

| 项目 | 实际结果 |
| --- | --- |
| Agent 每轮输出预算 | 使用模型能力中的 `max_output_tokens` |
| DeepSeek V4 Flash wire 输出预算 | 每轮均为 `8192` |
| 请求 reasoning 档位 | `low` |
| wire reasoning 字段 | `reasoning_effort=low`，报告确认已发送 |
| 并行工具字段 | Provider 未配置时不伪造发送值；临时实验可发送但未证明模型必然并行 |

### 9.2 Provider 原始阶段和失败轮次已可观测

Provider 流现在区分以下阶段，并保留请求/响应字节、HTTP 状态、wire 输出预算和尝试次数：

- `request_started`
- `response_head`
- `first_byte`
- `first_event`
- `completed`

失败轮次不会再把响应头或模型结束事件伪装为网络首字节。实际 OpenCode 失败报告中：

- `firstByteAt` 为空；
- `firstByteSource=unavailable_after_response_head`；
- 失败模型轮次保留 `failureHttpStatus=522`；
- Provider 尝试次数为 `1`，重试次数为 `0`。

一次 522 自动重试实验中，两次尝试均返回 522，只把失败等待扩大到约 66 秒，因此该重试已撤回。当前不会对这类失败做无意义自动重试。

### 9.3 明确只读首轮的意图阶段优化

对“首轮、明确命名文件、明确要求读取/检查/总结、明确禁止修改任何项目文件、且没有自定义意图”的窄场景，使用确定性只读意图，不再调用只会重复得出禁写结论的意图模型。

该短路不会应用于：

- “不要修改 Provider 配置”之类局部限制；
- 普通语义讨论或未明确命名文件的请求；
- 后续轮；
- 自定义项目意图。

真实结果：

| 场景 | 优化前意图阶段 | 优化后意图阶段 |
| --- | ---: | ---: |
| 单文件严格只读 | `8,320ms` | `34ms` |
| 三文件严格只读 | `8,502ms` | `28～30ms` |
| 实际 OpenCode `ds` 单文件失败样本 | 原路径为秒级模型调用 | `31～33ms` |

### 9.4 三文件串行回合治理

三文件夹具始终要求：三个唯一 `read_file`、顺序不变、无重复读取、三个固定标记全部返回。未缩短任务目标或更换验收条件。

### 9.5 Git 恢复点固定成本治理

在意图和模型回合优化后，真实报告暴露出新的本地主因：临时 workspace 的 `workspace_snapshot` 持续占用约 `6.7～7.0s`，而文件工具本身仅为 `6～7ms`。

对同一临时 Storydex workspace 进行逐条 Git 子进程计时后确认：旧 `begin_turn` 冷态启动 `107` 个 Git 子进程，暖态仍启动 `52` 个；大量时间消耗在每条内部命令前重复执行 `rev-parse --show-toplevel`，以及为恢复点读取两遍 UI 才需要的提交历史和图谱。

本轮新增 Agent 专用轻量恢复点入口。它仍然：

- 在同一 worktree 锁内执行；
- 校验项目目录与 Git top-level 完全一致；
- 初始化本地仓库、分支、本地身份和 `.gitignore`；
- 清理旧版本误跟踪的 `.storydex/.agent/` 与 `.storydex/.cache/`；
- 在需要时创建真实的首个本地恢复提交；
- 记录本轮开始时的 changed-file 状态和文件指纹。

它不再为恢复点加载提交历史、图谱，也不在已经验证的同一锁定操作中重复执行仓库边界子进程。

直接计时结果：

| 暖态 Git 子进程 | `52` | `12` |

### 9.8 当前阶段结论与后续范围

本阶段已经闭环：

- 输出预算和 reasoning 的真实 wire 传递；
- Provider 原始响应阶段与失败尝试观测；
- 明确只读首轮的意图模型固定成本；
- 代表性多文件任务的串行模型回合；
- Agent Git 恢复点的重复子进程固定成本；
- 实际 OpenCode 522 的本地与上游耗时边界。
- 长项目上下文候选排序的真实瓶颈定位与最小并发优化。

尚未因此宣称整个治理计划全部完成。后续阶段仍应覆盖：

- scoped 写入任务的副作用、恢复点和提交确认；
- 流中断、权限拒绝、取消和继续执行；
- 同 session 后续轮的历史重传与证据复用；
- 模型或 Provider 版本变化后，多文件批量读取是否仍保持 2 回合；
- 不同磁盘冷启动、项目规模和模型版本下，上下文候选排序是否仍保持稳定；若继续优化，必须先用同口径真实夹具确认新的主因。

在 `ds/deepseek-v4-flash` 上游恢复前，不应增加 522 自动重试或用更长超时掩盖故障；应保留单次尝试、明确 HTTP 状态和可复现失败报告。

### 9.9 2026-08-16 Rust Agent 迁移前复核

本轮重新构建当前 `HEAD` 的 Rust bridge，并通过 Storydex 正常 Backend HTTP/SSE 入口运行真实模型场景。配置副本和小说项目均位于临时目录，未写回源配置，也未读写真实用户项目。

第一轮从 OpenCode 的 `opencode.json` 选择 `ds/deepseek-v4-flash` 并转换到临时 Coomi Home。两次严格只读调用均产生相同边界：

| 项目 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 总耗时 | `25,857ms` | `26,519ms` |
| Provider 等待 | `20,393ms` | `20,411ms` |
| 模型回合 / 工具调用 | `1 / 0` | `1 / 0` |
| Provider 尝试 / 重试 | `1 / 0` | `1 / 0` |
| HTTP 结果 | `522` | `522` |
| capability | `read_only` | `read_only` |
| RouteHints 操作信号 | `read + write + scope_exclusion` | `read + no_write` |

OpenCode CLI 对同一个 `ds` Provider 的无工具完整请求也在约 `20s` 收到 HTTP 522。该结果只能证明 `ds` 所指线路在该时段返回 522，不代表所有名为 `deepseek-v4-flash` 的 Provider 都不可用。

后续核对发现，Storydex 桌面端实际激活的是自身 `providers.json` 中的 `OPENCODE/deepseek-v4-flash`。非敏感等值比较确认，`OPENCODE` 与 OpenCode 配置中的 `ds` 使用不同的 `base_url` 和 API Key；最近一次桌面端会话也记录为 `provider_id=OPENCODE` 并正常产生模型输出。因此，先前把 `ds` 的 522 外推为“桌面端实际 Provider 不可用”是错误的。

改用桌面端实际生效的 `OPENCODE` Provider 后，严格只读场景通过：

| 项目 | 实际结果 |
| --- | ---: |
| 总耗时 | `12,180ms` |
| Provider 等待 / 模型生成 | `3,878ms / 5,542ms` |
| 模型回合 / 工具调用 | `2 / 1` |
| Provider HTTP / 重试 | `200 / 0` |
| 工具序列 | `read_file` |
| capability / RouteHints | `read_only / read + no_write` |
| 固定证据标记 | 已返回 |

同一个 `OPENCODE` Provider 的角色字段定向编辑也完成了实际读写闭环：一次保留报告的运行耗时 `23,136ms`，共 `6` 个模型回合、`5` 次工具调用，Provider 全程 HTTP 200、零重试；工具序列为 `read_file → edit_file（失败）→ search → edit_file（成功）→ read_file`。最终文件同时满足新字段已写入、旧字段已移除和保留字段未丢失，但严格基线仍因中途工具错误判为失败，不能表述为“零错误 scoped-write parity 已通过”。重复诊断中也出现过无工具错误的完成轮次，说明该现象不是稳定的 Provider 或 Rust 工具不可用；在获得可复现错误参数前，不据此修改 `edit_file` 实现。

真实报告同时暴露了一个本地可复现问题：“不要修改任何文件”被当成正向写入，“不要使用其他工具”又被当成写入范围排除，使主模型收到了与 `read_only` capability 相冲突的 RouteHints。现已将操作信号改为按分句识别否定前缀，并区分项目级禁写与命名/局部排除；修复后的相同主链路报告确认 RouteHints 只保留 `read + no_write`。

基线脚本还修复了一个诊断缺陷：SSE 已完成、但后置严格验收失败时，现在仍会先写入脱敏 `baseline-report.json` 并记录验收错误，不再只返回一条无法复盘的终端错误。当前结论是严格只读 live 已通过；scoped-write 已完成最终文件闭环，但其零中途错误门槛尚未稳定通过。

`storydex-agentd` 首个只读配置切片完成后，又从当前代码重跑了相同 Storydex 主链路：`OPENCODE/deepseek-v4-flash` 总耗时 `10,462ms`，Provider 等待/生成 `2,669ms / 1,769ms`，2 个模型回合、1 次 `read_file`、零工具错误、零重试，最终 `AgentCompleted`；`capability=read_only`，RouteHints 仍为 `read + no_write`。这次结果继续证明 Storydex 实际配置可用，但不代表 Agent HTTP/SSE 已由 `storydex-agentd` 接管；当前 Rust 服务仅完成 health 和脱敏 Provider 状态切片。

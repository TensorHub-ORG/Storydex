## 1. 目标与原则

本计划的目标是通过真实运行证据，回答三个问题：

1. Storydex 的慢响应主要由独立意图调用、主模型回合、Provider、Git 恢复点还是上下文装配造成；
2. 哪些意图字段确实提升了小说创作质量，哪些只是让主模型重复理解同一请求；
3. 如何在不牺牲角色卡、世界书和章节证据完整性的前提下，建立由工具层强制执行的写入安全边界。

计划不预设“删除意图模型”或“保留意图模型”必然正确。每个架构分支都必须使用相同入口、相同任务目标和隔离项目进行对照，最终由端到端质量、延迟和安全数据决定。模型能力足够时，应优先让模型直接处理真实请求和证据；但如果某个专用结构化工作流确实需要额外判定，可以保留该判定，不为追求单一架构而牺牲功能。

所有结论分为三类：

- **代码/实测事实**：能由本地代码、测试或脱敏运行报告直接复核；
- **外部资料支持的判断**：成熟 Agent 的官方资料所显示的职责划分或常见机制；
- **待验证假设**：必须通过新一轮真实调用验证，不能在计划阶段当作结论。

## 2. 当前基线与问题假设

### 2.1 已确认的代码与运行事实

- 当前入口是 `RunAccepted -> 独立意图 LLM -> TurnContract/上下文 -> Git snapshot -> Rust bridge -> 主 Agent 多轮模型与工具`。意图阶段完成后才开始 Contract 和上下文装配，见 `apps/backend/api/routes_agent.py`。
- `storydex_intent_service.py` 输出领域、效果、操作类型、目标、约束、复杂度、澄清决定、技能、资产目录和知识写入模式；这些字段仍被生成、知识绑定、上下文和任务清单逻辑消费。
- 独立意图调用已有真实样本约 `3.4～6.9s`，某次完整调用约 `19.5s`、意图阶段约 `4.4s`。Qwen 样本总耗时约 `24.8s`、Provider 等待约 `16.7s`，文件工具只有毫秒级。
- 明确只读短路样本已从约 `8.3～8.5s` 降至约 `28～34ms`；多个独立读取在提示约束生效时可由四个模型回合降为两个，但这不是协议级并行保证。
- 当前角色卡和世界书仍存在固定短预览，正确文件被选中时，文件中后部的关键字段仍可能未进入初始上下文。`read_file` 已支持 revision、span、`hasMore` 和分页续读。
- `CONTEXT_LRU_ENABLED`、`CONTEXT_TOKEN_BUDGET_REAL` 和 `JIT_CONTEXT_LOADING_ENABLED` 默认未启用；它们是否改善端到端速度仍待测量。
- Python 服务普通聊天默认 `full_access`；`intent.canWrite=False` 或 `directFileWrites=False` 目前不会自动成为工具层只读边界。Rust 中 `allowedWriteRoots=[]` 表示不启用 scoped 根目录检查，而不是禁止写入。相关位置见 `apps/backend/services/coomi_agent_service.py`、`vendor/coomi-rs/storydex-bridge/src/main.rs` 和 `vendor/coomi-rs/security/src/lib.rs`。

### 2.2 需要验证的核心假设

H1. 对普通问答、明确读取和明确修改，主模型直接理解请求可省去意图阶段固定成本，且不会显著增加误写或无效澄清。

H2. 少量确定性定位提示（活动文件、显式路径、目录/标题/实体索引）比一次性自然语言分类更适合给小说 Agent 提供定位帮助；但它是否足以替代当前所有 IntentFrame 字段，需要按专用工作流分别验证。

H3. 动态工具暴露和工具层 CapabilityPolicy 能减少错误工具回合，并比“让意图模型决定能否写入”更可靠；该假设必须通过越界、只读和 shell 绕过测试证明。

H4. 结构地图 + 命中片段 + revisioned 按需读取，比固定头部预览同时具有更好的证据覆盖和可接受的 Token/延迟；不能仅凭平均上下文装配时间判断。

H5. 在 Contract 依赖被解耦后，意图判定可以并行、延后或仅对少数歧义/专用流程触发；否则所谓“并行意图”只是在等待另一条仍然阻塞的依赖。

## 3. 阶段 0：真实基线与观测准备

这一阶段不改变产品语义，先建立可复核的当前版本基线。若现有 Trace 无法区分某个阶段，先补最小观测字段，再进行架构实验。

### 3.1 OpenCode `deepseek-v4-flash` 新对话实测

使用当前机器已有的 OpenCode Provider 配置副本，通过 Storydex 正常 HTTP/SSE Agent API，在临时 workspace 中新建独立会话。不得修改源 OpenCode 配置，不得把凭证、Authorization、完整提示词、reasoning 正文或小说正文写入报告。

第一轮只做代表性夹具，随后根据结果增删场景：

1. 明确修改角色卡中后部的“核心动机”字段；
2. 明确读取角色卡或世界书中后部字段，并要求引用证据；
3. 明确禁止任何写入的只读总结；
4. 模糊目标，需要澄清的请求；
5. 跨章节查找人物、事件和时间关系；
6. 同一 session 的后续追问，观察历史和证据复用；
7. 明确越界路径、shell/patch 绕过和 `allowedWriteRoots=[]` 的权限行为。

每个场景先运行 3 次检查链路，再按 Provider 稳定性决定是否扩展到 10～30 次。冷态、暖态、首轮和后续轮必须分开统计，运行顺序随机交错，避免把一次 Provider 波动误判为架构收益。

### 3.2 最小观测协议

每个脱敏报告至少包含：总耗时、首个可见输出、每轮开始/结束、Provider 首响应与持续生成时间（若协议可提供）、模型回合数、工具序列和耗时、输入/输出/reasoning/cache Token、重试次数及阶段、权限模式、最终停止原因、是否产生写入、目标文件 revision 和证据 span。

报告还要记录“为什么进入下一回合”：新证据、工具错误、用户补充、模型继续生成或无进展。无法测量的字段必须标记为 unavailable，不得用模型完成时间伪装网络首字节。

## 4. 阶段 1：架构分支对照

所有分支都保留现有 API、session、Git 恢复和回滚语义；只切换意图阶段、上下文策略或工具暴露策略。先完成安全护栏，再运行允许写入的分支。

### 4.1 分支 A：当前实现

独立 Intent LLM 串行执行，作为质量、延迟、澄清率、工具回合和安全行为的基线。记录 Provider 异常时的保守降级比例。

### 4.2 分支 B：主模型直达

普通请求跳过独立意图 LLM，主模型接收完整用户请求、少量项目定位提示和可用工具。保留兼容性的 IntentFrame 默认值，但不让默认值授予权限，也不让缺失字段静默触发专用写流程。只在隔离 workspace、feature flag 和可回滚配置下启用。

### 4.3 分支 C：规则 RouteHints + 主模型 + 强权限

使用零成本、可审计规则生成 advisory hints：显式路径、活动文件、文件类型、标题/字段/实体命中、明确的只读或写入模式。RouteHints 只帮助定位和减少无关工具，不得决定 `canWrite`、澄清结论或扩大权限。权限由用户会话模式和工具层 CapabilityPolicy 独立决定。

### 4.4 分支 D：按需专用判定

在 C 的基础上，只有进入章节创建、知识候选提取、显式绑定、复杂任务清单等确需结构化输入的流程，才调用专用分类/判定。该调用可延后到主模型确认目标后，或与不依赖它的上下文准备并行。若实测显示额外判定没有质量收益，应继续收缩其范围。

### 4.5 可选分支 E：并行与动态工具暴露

仅在真实 Provider 支持并发工具调用且观测能证明收益时启用。对互不依赖的只读读取允许同一响应发起多个调用；依赖前一结果的操作保持串行。动态工具集合应依据显式权限、工作流状态和已确认目标裁剪；不能因为一次错误路由让主模型失去自救能力，必要时提供只读搜索/读取工具作为通用后备。

## 5. 阶段 2：权限与写入安全先行

这是所有主模型直达或动态工具实验的前置门槛。目标不是把自然语言分类做得更“像权限系统”，而是让权限在模型输出错误时仍然成立。

1. 将权限语义改为显式模式：`read_only`、`scoped_write`、`workspace_write`、`full_access`；明确区分未配置 roots、禁止所有写和允许指定 roots。
2. Python registry、Rust bridge、底层 SecurityPolicy 使用同一 CapabilityPolicy；每次写入、编辑、shell、patch 和 Storydex mutator 均重新检查。
3. 只读模式不暴露或拒绝所有 mutator；scoped write 拒绝 shell/patch 等绕过路径，并校验规范化路径、符号链接/junction 和目标 revision。
4. 自然语言中的“不要修改”只能收紧当前权限；任何扩大权限的动作必须来自显式 UI/会话操作或审批事件。
5. 增加回归测试和隔离真实测试：只读写入、越界写、空 roots、shell 绕过、权限切换、Provider 异常和恢复重放必须零违规。Rust 聚焦权限映射测试已通过，但不替代上层默认权限测试。

## 6. 阶段 3：上下文与证据获取

### 6.1 初始上下文

把固定头部预览逐步替换为低成本结构地图：路径、文档类型、Markdown 标题/字段、角色别名与关系、世界书条目、章节顺序、revision 和命中 span。地图只放定位证据，不承载整篇正文。

### 6.2 按需读取与覆盖率

主模型先读取命中片段，再根据事实核验、修改范围和连续性需要扩大窗口或分页读取。编辑前必须读取目标 revision；写入后记录实际变更字段和证据引用。对“总结全部”“检查项目是否存在”这类声明，增加证据覆盖率账本，区分已读、命中、未读和不适用，而不是只依赖模型口头说明。

### 6.3 Token、LRU 和 JIT

先以 shadow accounting 记录预算，不直接整体打开新策略。只有当真实报告证明历史重传或无关上下文占据主要成本时，才逐项启用 Token budget、LRU 或 JIT，并用相同夹具验证关键字段命中率没有下降。任何截断策略都必须返回可继续读取的信息，而不是静默丢弃文件中部内容。

## 7. 阶段 4：调度、停止与恢复

根据阶段 0 的回合证据决定是否调整：

- 给互不依赖的只读工具调用提供并行提示或协议级批量工具；
- 对重复读取、相同 revision、无新增证据和连续工具错误设置渐进式止损；
- 将 Provider 超时、流中断、重试和工具副作用纳入同一个可恢复状态机；
- 检查点必须记录权限、目标、计划、证据和已完成动作，继续执行不能无条件重放写入。

这些边界使用“相对于基线的无进展回合、p95、错误率和恢复正确性”评估，具体数值可在首次真实运行后调整，不在计划阶段固定成不适合不同模型的硬阈值。

## 8. 评测指标与决策门槛

### 8.1 质量

- 目标文件/字段定位准确率；
- 角色卡、世界书和章节关键内容命中率；
- 事实引用的 revision/span 覆盖率；
- 修改范围准确率、无关内容变更率；
- 合理澄清率与错误澄清率；
- 复杂工作流完成率、恢复后重复写入率。

### 8.2 性能

- 端到端、首输出、各阶段 p50/p95；
- Provider 首响应、持续生成、重试等待；
- 模型回合、工具回合、重复调用和无进展回合；
- 逻辑输入、实际传输输入、输出、reasoning 和缓存 Token；
- 上下文装配、索引查询、Git snapshot 和 bridge 初始化耗时。

### 8.3 安全

只读写入、越界写、shell/patch 绕过、非法 revision 写入、权限降级绕过和恢复重放均采用零容忍。任一分支出现安全违规，立即停止扩大样本，保留报告并修复根因。

### 8.4 决策方式

不以单次最快或单一平均值决定方案。候选方案至少应在主要场景上达到与基线相当或更好的质量，显著减少固定意图等待或无进展回合，并通过全部安全门槛。若质量和速度互相冲突，按“安全 > 目标字段/事实正确性 > 可恢复性 > 延迟”排序；具体权重可在真实业务样本后调整。

## 9. 动态调整规则

每轮实验结束后先看数据，再决定是否进入下一阶段：

- 若 Intent LLM 占比低且专用字段显著改善质量，保留其窄范围调用，优先优化并行或延后时机；
- 若 Intent LLM 占比高但与主模型判断高度重复，扩大 B/C 的普通请求覆盖；
- 若主模型直达增加澄清或误写，先检查 RouteHints、工具描述和权限策略，不直接恢复全量分类器；
- 若上下文装配或索引成为主要成本，暂停模型架构争论，先优化快照、缓存和增量索引；
- 若 Provider 等待占绝大多数，优先核对真实 wire 配置、协议兼容和重试，不把上游慢误归因于 Storydex；
- 若模型能力、工具协议或 Provider 行为变化，允许新增实验分支，但必须保留 A 基线和同口径报告。

## 10. 交付物、回滚与发布顺序

每个阶段交付脱敏报告、聚焦测试、变更说明和可关闭的 feature flag。推荐顺序为：

1. 观测和安全边界；
2. OpenCode `deepseek-v4-flash` 当前基线；
3. 主模型直达与 RouteHints 隔离实验；
4. 上下文结构地图和按需读取；
5. 专用工作流判定迁移；
6. 并行工具、停止和恢复优化；
7. 经过真实回归后逐步扩大默认范围。

任何阶段如果质量、安全或恢复性退化，关闭对应 flag 即可回到 A；不通过删除历史、静默 fallback 或放宽权限来掩盖退化。计划完成的标志是有真实前后报告、可解释的收益或失败原因、完整回归通过，并形成明确的架构决策记录。
